Télécommande & gants de Didier — architecture de l'interface

PROPOSÉ 01/11/2026 — rien n'est codé Une seule idée : séparer ce qui conduit le robot de ce qui s'affiche, puis brancher autant d'écrans qu'on veut sur le même cœur.

1Aujourd'hui : l'écran tient le volant

Dans dadou_control_ros, c'est la boucle de l'interface tkinter qui lit le gamepad et les gants. Les commandes roues passent donc à travers l'interface graphique.

2La cible : trois couches qui ne se connaissent presque pas

Chaque appareil (télécommande, gant 2) fait tourner les mêmes trois couches. Elles ne se parlent que par des topics ROS : on peut arrêter ou remplacer un écran sans toucher à la conduite.

sécurité / conduitelogique pureafficheurs (interchangeables)
Ce que ça garantit : si un écran plante, on obtient un menu figé — jamais un mouvement figé. C'est la même discipline que celle déjà actée pour le boîtier RP2040 (la conduite ne passe jamais par le menu).

3Qui tourne où

Quatre machines. Le RP2040 n'est qu'une source de boutons : aucun logiciel de menu n'y vit (OLED mis de côté le 01/11). Chaque appareil a son propre espace de noms (remote/…, glove2/…) : deux menus, deux états.

En simulation, les cœurs tournent dans le conteneur sim (domain 43), sans aucun matériel : le menu se teste depuis la page scène avec le même code que sur les Pi.

4Une action de bout en bout

Exemple : David touche « Parle » sur l'écran, puis l'opérateur clique la même chose dans la page scène. Les deux chemins entrent par la même porte (ui_action) — c'est le cœur qui décide.

5Le chemin roues ne change pas — il est seulement libéré de l'écran

Les priorités et les arrêts déjà validés restent tels quels. La seule modification : c'est le node d'entrées (et non plus l'interface) qui publie la conduite de la télécommande.

Règle projet : le lot 1 (déplacement de la lecture des entrées) touche le chemin roues → validation en simulation, puis protocole caméra roues hors sol, avant tout usage au sol.

6Les écrans : même état, plus ou moins de détail

Le cœur publie tout l'état ; chaque afficheur choisit ce qu'il montre. Le gant 2 est discret : il montre moins, il ne sait pas moins.

Essai décidé pour l'afficheur sans X11

pygame (SDL2 kmsdrm)

  • ✔ léger, tactile natif, dessine directement sur l'écran
  • ✔ robuste, peu de dépendances
  • ✘ deux interfaces à écrire : pygame pour le Pi, HTML pour la page scène

WPE WebKit « cog »

  • ✔ navigateur embarqué sans X11 (DRM direct)
  • ✔ une seule interface HTML pour le Pi ET la page scène
  • ✘ plus lourd — tenue sur 512 Mo non vérifiée
Critères de l'essai, sur la vraie carte : mémoire mesurée et réactivité du toucher. Si cog tient sur la Zero 2 W, il gagne. Le choix est réversible : l'afficheur n'est qu'un client de ui_state.
